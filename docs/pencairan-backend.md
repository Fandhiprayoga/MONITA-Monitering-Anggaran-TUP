# Backend pengajuan v1.5 — integration and operations

## Integration contract

- Keterangan di bawah pilihan DRK menampilkan `N DRK ditemukan`, diperbarui saat daftar unit/pencarian berubah (termasuk `0 DRK ditemukan`). Detail teknis kolom spreadsheet tidak ditampilkan pada bantuan Unit/DRK; pesan pemuatan dan kegagalan sumber tetap ditampilkan.

- Pilihan Unit pada form baru admin dan pilihan DRK pada semua form baru/edit menggunakan Select2 dengan pencarian dan bahasa Indonesia. Aset Select2 dimuat dari CDN setelah jQuery dari layout. Pilihan DRK mengisi header/saldo melalui handler yang sama; pergantian unit mereset pilihan dan memperbarui opsi Select2. Kolom Cari DRK terpisah disembunyikan saat Select2 aktif; jika aset gagal dimuat, peringatan tampil dan select biasa serta kolom Cari DRK tetap dapat digunakan.

- Menu Transaksi memakai view terpisah untuk Impresfund, Beban, dan Honor, dengan komponen daftar/filter bersama. Jenis pada URL transaksi menentukan jenis daftar, bukan query `jenis`. Tautan detail membawa query `menu` (`pengajuan`, `verifikasi`, atau `transaksi`); konteks admin ini dipertahankan saat edit/simpan/submit agar sidebar dan tombol kembali mengikuti menu asal. Pengajuan tetap satu menu; tombol kembali dari konteks Pengajuan memfilter jenis yang sama dan memilih tab aktif/nonaktif sesuai status.
- Header tab **SIMKUG** sama dengan tab Detail untuk semua jenis pengajuan. Pada Beban/Honor, tombol salin per nilai tetap tersedia di bagian **Salin data header**. Rincian SIMKUG Beban/Honor readonly dan tersedia pada status `verified`, serta pada status `completed` bagi admin. Impresfund memakai satu baris total dengan urutan **Kode Akun, Nama Akun, DC, Keterangan, Nilai, Kode PP, Nama PP, Kode DRK, Nama DRK**. Kolom selain DC bersumber dari data pengajuan dan readonly; ubah sumbernya melalui edit pengajuan. DC kosong sampai admin memilih `D`/`C`. Hanya DC yang dikirim dan disimpan melalui `PATCH /pencairan/pengajuan/{uuid}/simkug` dengan `lock_version`; nilai sumber selalu ditampilkan dari pengajuan. Penyimpanan menaikkan versi dan mencatat sebelum/sesudah pada riwayat `simkug`. Submit revisi baru mereset data SIMKUG; riwayat lama tetap tersimpan. Impresfund `completed` tetap menampilkan SIMKUG readonly bagi admin dan pengguna PP.
- Penyalinan Impresfund dilakukan langsung dari pilihan spreadsheet grid dengan Ctrl+C/Cmd+C; tidak ada section Salin Baris terpisah. Tidak ada pengiriman langsung ke SIMKUG. Terapkan migration `2026_11_05_000001_add_simkug_data_to_pengajuans` sebelum menggunakan fitur ini.
- Tabel SIMKUG Impresfund memakai spreadsheet grid seperti Detail: pilih sel/rentang dengan klik/drag atau Shift+panah, pilih baris/kolom melalui header, Ctrl+C menyalin TSV. Semua kolom selain DC dinonaktifkan karena berasal dari data pengajuan; admin hanya dapat memilih DC melalui dropdown D/C. Jumlah baris tetap satu dan pilihan DC disimpan dengan tombol Simpan Data SIMKUG.
- Session/CSRF-protected routes to `PencairanWorkflowController` are registered: `store`, `update`, `submit`, `returnToUser`, `verify`, `cancel`, `complete`, `attachment`. Writes use throttling (60/minute). Forms, scoped lists, detail/revision timeline, verification and transaction actions are connected. Tune throttling for production load.
- All successful JSON writes return `{id, lock_version, redirect_url}`; create uses 201, other operations 200. Native create redirects to detail; other native actions redirect back with `success` flash. Validation uses 422, access 403, stale state/version or mismatched idempotency 409, unavailable/invalid source balances 503.
- `PencairanPengajuan` uses `pengajuans`. Status is a string; use `statusLabel()`. `details()` is an instance per-type relation and `detailRows(): array` emits raw Indonesian grid records (blank subtotal means automatic). Use `histories`, `revisions`, `completion.attachments` for detail pages. For eager loading use explicit `impresfundDetails`, `bebanDetails`, `honorDetails` (not dynamic `details`); `detailRows()` uses those loaded collections. Mixed-type queues should display parent totals only.
- `PencairanService::actor(Request)` validates spreadsheet session. Use `PencairanPengajuan::forActor($actor)` for all read/list queries, and `authorize(Request, $pengajuan)` on detail/history/revision endpoints. These must never expose records from other PP. Actor comes from session, never request data. Filter server queries by `jenis`, `status`, `tahun_anggaran`, `triwulan`, PP (admin only), number; paginate, and order verification queue by `last_submitted_at`. DRK form balances use the spreadsheet's `saldo_awal`, database `total_bruto` summed across all form types for matching PP/year/TW/DRK with statuses submitted/verified/completed, and `saldo_terkini = saldo_awal - anggaran_terpakai`. Draft/returned/cancelled do not reserve budget. Submit/verify recompute this budget server-side and exclude the current pengajuan from the other commitments being checked.
- Create accepts `jenis`, optional `drk_id`, optional `uraian_pengajuan`, `details` array (may be empty), and `unit_kode_pp` for the selected submission unit. Admin unit options are read fresh from `users!B2:C` (B = PP code, C = PP name), normalized and deduplicated by code, without config fallback. `GET /pencairan/drk-options?unit_kode_pp=...` validates the role/unit and returns `{options: [...]}` for the current year/TW. Changing unit clears the selected DRK/header and refreshes DRK options without clearing detail rows. The selected unit is fixed after the first successful draft save; update cannot change unit or type. Browser readonly fields/totals remain ignored; unit name is resolved on the server.
- Users can create/edit/submit only for their session PP. Admins can select any unit present in sheet users, including admins without a session PP, and edit/submit draft/returned across units. Admins can also edit submitted, verified, and completed submissions without changing their status; completion records and submitted revision snapshots remain intact. Admin can cancel drafts/submitted/returned with a mandatory remark. Actor identity and audit attribution always remain the logged-in admin, not the selected unit. Period, saldo, lock-version, and DRK ownership checks remain unchanged. No additional restriction on same-admin verification/completion has been introduced.
- Submit uses saved data only, `lock_version`, mandatory `idempotency_key`, optional accepted `confirmed`. Return requires nonblank `remark` + accepted `confirmed`; verify/cancel require accepted `confirmed`; admin cancel also requires remark.
- Complete requires `completion_date` (Y-m-d), accepted `confirmed`, `lock_version`, `idempotency_key`; optional notes. The confirmation modal has no attachment upload; the API retains optional attachment support (up to five) and existing attachments remain downloadable. All external evidence/TUB reference fields are rejected. UI supplies today's default date. Idempotent retries must resend the identical original payload, including original lock version and identical file names/bytes if sent through the API. A new revision/new operation must use a new key. CSRF token itself does not affect payload hash.

## Source configuration — mandatory production review

- `PENGAJUAN_BUDGET_YEAR` defaults to **fixed 2026**. `GOOGLE_SPREADSHEET_ID` is only that year's source, not whatever year the server happens to be in. Update the configured binding deliberately when rolling over the source; archive the previous source first.
- Annual environment keys `GOOGLE_SPREADSHEET_ID_YEAR_2025` and `GOOGLE_SPREADSHEET_ID_YEAR_2026` are mapped explicitly as archives when present. Add further explicit `year => spreadsheet ID` entries in `pencairan.archive_spreadsheet_ids` for historical queues. Unknown years fail closed with 503; there is no current-year/cache/snapshot fallback. Ensure the annual sheet exposes all four `RAW Data TW I/II/III/IV` tabs and historical balances remain maintained.
- New forms must call `getPencairanDrkOptions(kodePp, TW, year)` and submit its stable ID. Legacy `getUnitDrkOptions(kodePp, TW)` remains unchanged in signature/row IDs for existing callers; do not use its row ID for workflow drafts.
- Stable DRK ID = SHA-256(JSON([uppercase-trim PP filter, DRK TUP, account, type])). Sort/insert and label/SIMKUG changes do not change it. Changing a key component creates a new source identity. Duplicate identities are rejected, not silently chosen. PP filter is the authoritative first column in the fetched B:N range; readonly metadata PP cannot grant access. Missing/invalid balances remain null, never zero. Negative saldo blocks any positive submit.
- Fresh readonly lookup uses a 15-second network timeout / 5-second connect timeout and runs before DB write locks. It does not reserve or update Sheets. Multiple requests may independently pass against the same balance; snapshot timestamps document this limitation.

## Actors, numeric bounds and storage

- Default actor mapping = source namespace + exact username hash. Deployment must guarantee unique immutable usernames, including case; username rename otherwise creates a new local actor. Never use positional sheet rows as identity. If spreadsheet `no` is genuinely unique and immutable, enable `PENGAJUAN_ACTOR_NO_STABLE=true`; changing usernames then retains attribution. Do not switch mapping mode/namespace without a reviewed actor migration. The `no` field must never be renumbered. Audit stores local actor ID plus username/role at action time, never password/full session. Access remains PP-based after account handover. Existing spreadsheet account-management duplication rules are not changed by this backend.
- Indonesian numeric inputs only, max two decimal places, nonnegative except external saldo; input ceiling 10 billion, total ceiling 5 trillion, max 500 active rows. Product and totals use Brick Math exact decimals (already installed by the application's dependency tree); multiplication is half-up to cents. Computed per-row subtotal is also capped at 10 billion. Manual subtotal zero differs from automatic blank. Beban neto defaults in the form to bruto minus tax and can be overridden manually; the server accepts manual neto independently of bruto minus tax. Honor neto remains manual; identifiers remain text.
- All actions use compare-and-swap `lock_version`, transactions and 5 DB deadlock retries. SQLite obtains a writer lock before reading within the transition transaction; per-year counter initializes via insert-or-ignore and increments atomically. Numbers and revisions never change/reuse after cancel; snapshots/history are append-only in the application (direct operational DB access must also be restricted).
- Attachment disk defaults to `local` (Laravel's private app storage). **Never configure a public disk.** Actual MIME bytes, extension, count and size are validated. Random storage names, authenticated PP/admin downloads, no-store responses, and upload cleanup on DB failure/retry are implemented. Backups must cover DB + private files together. Retention/encryption/malware scanning, restore rehearsal and actual production driver concurrency UAT remain operational prerequisites; SQLite concurrency is covered by an isolated file-based subprocess test.
- Application time zone determines numbering and business dates (`Asia/Jakarta` in the current app). Completion lower bound follows latest active verification date after return/reverify, upper bound today; audit timestamps always record real server action time.

## Testing

### Seeder data dummy

- Jalankan `php artisan db:seed --class=PencairanPengajuanSeeder` setelah migration. Seeder ini juga dipanggil oleh `php artisan db:seed` pada environment `local`/`testing` saja; pemanggilan langsung di environment lain ditolak.
- Menghasilkan 54 pengajuan: unit SIF/KUG/AKA × impresfund/beban/honor × enam status. Setiap pengajuan memiliki tiga rincian (162 rincian total), dengan perhitungan desimal melalui `PencairanService::calculate`, snapshot anggaran, aktor dummy, riwayat, revisi submit, serta sembilan catatan penyelesaian. Contoh mencakup subtotal otomatis/manual, WNI/WNA, dan nomor rekening dengan nol awal. Tidak membuat lampiran fiktif maupun akun login spreadsheet.
- Pemanggilan ulang melewati pengajuan dummy yang sudah ada tanpa mengubahnya, menghapus data lain, atau mengulang nomor. Nomor mengikuti counter tahunan dan nomor terbesar yang telah tersimpan. Uraian berawalan `[DUMMY]` dan snapshot `dummy: true` membedakannya dari pengajuan nyata.
- DRK, saldo, penerima, rekening, dan identitas seluruhnya fiktif; tidak ada akses Google Sheets atau pembayaran. Data terlihat untuk pengguna dengan kode PP terkait dan admin. Untuk submit/verifikasi sungguhan, pilih DRK valid dari Google Sheets terlebih dahulu pada draft/returned; DRK dummy memang tidak lolos pemeriksaan sumber.

Tests use in-memory SQLite, mock Sheets, private fake storage; the concurrency test creates/migrates/removes only a new temporary SQLite file and starts isolated PHP workers. Actual registered routes and Blade pages are covered for all three types, user PP restrictions, admin actions, revisions and completion. Production-driver concurrency and operational acceptance still require UAT.

Validation: full Laravel suite 62 tests / 886 assertions, JavaScript grid suite 12 tests, and Blade compilation pass. The scaffold root smoke test now checks the existing login redirect instead of HTTP 200. No real Google Sheets transactions or external payments are performed by tests.
